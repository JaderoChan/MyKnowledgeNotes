2. 静态变量如果在进入程序入口 `main()` 前初始化失败，抛出异常且未被捕获的话会引发 `std::terminal` 并直接终止程序。其中具有 **静态存储期** 的全局对象大多会在 `main()` 之前完成 **零初始化**，而动态初始化可能在 `main()` 之前初始化也可能被推迟。函数内的 `static` 变量（局部静态变量，动态初始化）则是在首次执行到该语句时被初始化。对于动态初始化的静态变量而言，如果首次初始化时抛出异常，则该静态变量被视为 **未完成初始化**，后续再次进入该语句时会尝试重新初始化。

4. **Doxygen** 的 `@details` 命令是用于对 `@brief` 命令进行补充说明的，既它是用于更详细的描述对象功能的说明而不是用于描述对象的实现细节。
5. **C++** 中 `std::move` 可以无条件把对象转成右值（准确说是 **xvalue**），表示：你可以搬走它的资源了。而 `std::forward` 是有条件地“保持原本值类别”转发，主要用于模版编程中实现完美转发。

    **详解**

    - `std::move` 用于触发移动语义，让移动构造/移动赋值有机会被调用。本质是类型转换，不做实际移动；真正移动发生在后续构造或赋值里。

        > **注意点**
        > - 被 move 之后的对象仍“有效”，但值通常不再可预期（只保证可析构、可赋值等）。
        > - 不要对 const 对象期待“移动优化”

    - `std::forward` 用于在模板中保留参数传入时的左右值属性。典型场景是转发引用（也叫万能引用）参数 `T&&`。

6. **C++** 中 `const T&` 可以绑定到左值或常量左值，也可以绑定到右值/临时值（如函数返回值）。当其绑定到临时值时，会将临时值的生命周期延长至这个引用本身的生命周期。 `T&` 只能绑定到非常量左值。`T&&` 通常用于绑定右值/临时值（同样会延长生命周期）或在模板编程中用于实现完美转发（万能引用）。

    **常见坑点**

    ```cpp
    const std::string& bad() {
        return std::string("tmp"); // 返回悬空引用，错误
    }
    ```

    这里临时对象在函数结束就销毁了，不会因为返回引用而继续活着。

7. **C++** 中将临时值赋值给 `const T&` 会比赋值给 `T` 少一次拷贝/移动构造的成本。不过现代 C++ 有拷贝消除（尤其是 **C++17** 的保证省略场景），很多时候编译器会把中间临时省掉，所以实际生成的产物中未必存在额外的拷贝/移动。
8. **Qt** 中 **QListWidget** 的 `takeItem()` 方法会返回指定位置元素的指针，并从列表中删除这个元素（但不会释放指针指向的内存，后续可以将方法返回得到的元素再插入回列表）。对于需要完全删除列表元素时（释放内存），推荐先通过 `takeItem()` 或其他 `QListWidget` 的成员方法得到需要被删除的元素指针，然后再进行 `delete`。注意，即使你在外部额外维护了一个列表存放元素指针，也不建议直接对其进行 `delete`，因为通过 `QListWidget` 的成员方法取出元素后再进行删除更加符合其功能语义（将元素的所有权转交给你，再安全删除，避免 `QListWidget` 内部可能存在的悬空引用风险）。
9. **Qt** `drag/drop` 事件中，`accept()` 和 `acceptProposedAction()` 方法的区别在于后者不仅表示接受事件，还明确采用系统当前建议的拖放动作。对于具体行为而言，`acceptProposedAction()` 实际上做了两件事：首先把当前实际动作设为 **proposedAction**（例如 Copy/Move/Link 之一），而后调用 `accept()` 标记事件已被处理。
10. **C++** 中 `dynamic_cast` 用于 **运行时安全地向下转换**。

    **适用场景**

    - 基类指针或引用，实际对象类型不确定时。比如有 Base*，实际可能是 A 或 B，你需要只在它真的是 A 时调用 A 的接口。
    - 需要多态层次里做类型分流时。当你无法通过虚函数设计解决，需要根据真实类型走不同分支时。
    - 需要安全失败机制时

    **特点**

    - 指针版失败会返回 `nullptr`
    - 引用版失败会抛出 `std::bad_cast` 异常

    **不建议的场景**

    - 你已经百分百确定类型。可用 `static_cast`（更快，但不做运行时检查）。
    - 可以用虚函数/接口多态解决。优先多态，少做类型判断，设计更干净。
    - 频繁高性能路径。`dynamic_cast` 有运行时开销，热路径里慎用。

    **前提条件**

    - 基类必须是多态类型（至少有一个虚函数函数，通常虚析构）。
    - 只能在有继承关系的类型间使用。

11. **Qt** 中 **QUrl** 的 `isLocalFile()` 方法对 **本地路径** 返回真，并不区分是文件还是文件夹。

1. **C/C++** 中 `getc()` 和 `fgetc` 函数在作用与用法上相同。但 `fgetc()` 保证是一个函数，有固定的函数调用开销；而 `getc()` 可以被实现为宏（也可以是函数），宏展开后可能避免函数调用的开销，但可能会多次求值参数。因此：

    ```c
    // 不要对 getc 传入有副作用的表达式
    getc(fp++);  // 危险：若 getc 是宏，fp++ 可能被求值多次
    fgetc(fp++); // 安全：fgetc 保证是函数
    ```

    推荐使用 `fgetc()`，语义更明确，使用也更安全，并且在现代编译器实现中，其与 `getc()` 几乎没有性能差异。

2. **C/C++** 对一个数组名进行强转后，得到的是强转后的指针地址，而不是指向的内存数据。例如

    ```c
    uint8_t buf[4] = {0};
    uint32_t num = (uint32_t) buf; // 错误
    ```

    `buf` 是数组名，会退化为 `char*` 指针，`(uint32_t)` 强转的是指针的地址值，而不是缓冲区里的数据。正确做法是使用 `memcpy()`：

    ```c
    memcpy(&num, buf, sizeof(uint32_t));
    ```

    直接用指针转换再解引用虽然在很多平台能工作，但属于未定义行为（违反严格别名规则）：

    ```c
    uint32_t num = *(uint32_t*) buf;
    ```

3. **C 标准** 明确规定任何对象都可以通过 `char*` 访问（**C11 §6.3.2.3 / §6.5**），这是严格别名规则的特殊豁免。因此对于 `fread()` 及类似函数可以直接：

    ```c
    uint32_t num = 0;
    FILE* file;
    // ...
    fread((char*) &num, sizeof(uint32_t), file);
    ```

    而不需要引入额外的 `char*` 缓冲区等。

4. **C/C++** `fread()`/`fwrite()` 函数的二，三参数（`size_t size, size_t nitem`），分别是每个元素的字节大小与要读取的元素个数。返回值是成功读取的元素个数（不是字节数）。
5. **C** 语言也可以使用花括号 `{}` 创建 **块作用域**。可以用于限制临时变量的生命周期，避免命名冲突。此外 `switch` 的 `case` 本身不引入作用域，当需要在 `case` 中创建临时变量时，也要使用 `{}` 创建块作用域。
6. 对于多语句宏，需要使用 `do { ... } while(0)` 写法，其主要是避免在 `if-else` 场景下出错。例如

    ```c
    #define MACRO_A(x) { do_something1(); do_something2(); }             // 不推荐
    #define MACRO_B(x) do { do_something1(); do_something2(); } while(0) // 推荐

    // 编译出错：因为 MACRO_A(X) 后的分号截断了 if 语句导致 else 找不到匹配的 if。
    // 如果不添加分号当然可以编译通过，但是语义不完整，不推荐!
    if (condition)
        MACRO_A(x);
    else
        do_something();

    // 正确：即使在宏后面添加分号也能正常工作。
    if (condition)
        MACRO_B(x);
    else
        do_something();
    ```

7. 在局部作用域可以通过 `#define` `#undef` 来临时声明一个宏，并且不会污染其他区域。
8. **C99** **VLA 数组**

    ```c
    int rows = 3, cols = 4;
    int (*arr)[cols] = malloc(rows * sizeof(*arr));

    // 直接用二维下标
    arr[i][j] = value;
    int v = arr[i][j];

    free(arr);
    ```

    对于上面的 VLA 数组 `arr`，其类型是 `int (*)[cols]`（运行时才确定列数的数组指针）。这种类型不能作为函数参数的类型声明（函数签名在编译期确定）。

9. **C** 语言中，任意指针到 `void*` 与 `void*` 到任意指针的转换都可以是隐式的，无需强转。但在 **C++** 中，后者（`void*` 到任意指针）必须进行强转。也就是说

    ```cpp
    void* p = malloc(100);
    int* q = p;                    // 只有 C 中才可行，C++ 中报错。
    int* q = static_cast<int*>(p); // 正确!
    ```

    此外，使用 **C++ 编译器** 时，即使此类代码使用 `extern "C"` 进行声明了，仍然需要进行强转，具体原因见下一条笔记。

10. **C/C++** 中 `extern "C"` 只影响链接符号的名称修饰（name mangling），让 C++ 编译器以 C 的方式处理符号名，使得 C 和 C++ 代码可以互相链接。

    但类型系统和语法规则仍然是 C++ 的，编译器还是用 C++ 规则解析代码。所以 `void*` 不能隐式转换到其他指针类型这条规则依然成立。

7. **MSVC** 中，调用动态库中的接口时可以不对接口声明标记为 `__declspec(dllimport)`，但是会损失性能。具体原因如下：

    **有 `__declspec(dllimport)` 时**：

    编译器知道该函数在动态库中，直接生成通过 **IAT（导入地址表）** 的间接调用：

    ```plaintext
    call → IAT 条目 → DLL 中的实际函数
    ```

    **无 `__declspec(dllimport)` 时**：

    编译器不知道函数来自动态库，链接器会为每个导入函数生成一个额外的 **跳转桩（thunk）**：

    ```plaintext
    call → thunk（额外跳转） → IAT 条目 → DLL 中的实际函数
    ```

    相比于有 `__declspec(dllimport)` 的情况多了一次跳转。

## 26-06-17

1. 字节序

    以某 16 位整数类型为例（浮点数或其他多字节数据类型同理），假设其十进制值为 `8`，则对应十六进制为 `0x00` `0x08`，其中 `0x08` 是低位字节，`0x00` 是高位字节。

    - 对于大端序，其在内存中的排列顺序为“**低地址存高字节，高地址存低字节**”，既 `00 08`。
    - 对于小端序，其在内存中的排列顺序为“**低地址存低字节，高地址存高字节**”，既 `08 00`。

    **其他**：

    - 网络字节序使用的是大端序
    - 现代大多数机器使用的都是小端序，因为小端序的“低地址存低字节”在 CPU 运算时永远从最低有效位开始计算，不用等待全部字节，在做类型转换时（例如 `int` 强转 `char*`）低地址直接是数值低位，不用做地址偏移调整。大端序的优势几乎只有人工读内存的时候更“好看".

    ```cpp
    struct RGB { uchar r, g, b; };

    static_assert(sizeof(RGB) == 3);

    std::vector<RGB> toRgbVector(const uchar* data, size_t byteSize)
    {
        if (byteSize % 3 != 0)
            throw std::runtime_error("size must be e multiple of 3");

        std::vector<RGB> out(byteSize / 3);
        memcpy(out.data(), data, byteSize);
        return out;
    }
    ```

    如果需要 **零拷贝视图**，那就不使用 `vector<RGB>` 而是使用 `std::span<const RGB>(reinterpret_cast<const RGB*>(data), byteSize / 3);`（`std::span` 于 **C++20** 正式加入标准库）。但是使用这个的前提是

    - `data` 必须真的按照 `RGB` 紧密排布
    - `RGB` 必须没有 padding
    - 对齐必须满足 `RGB` 的要求

    所以一般情况下推荐使用 `memcpy()` 生成对应数据类型的 `vector`。

4. **C++** 中 **SFINAE** 约束是 `Substitution Failure Is Not An Error`（替换失败非错误）。意思是：

    编译器在用模板实参去替换模板参数时，如果某个候选模板替换后不合法，这个候选会被“静默丢弃”，而不是立刻报错。然后编译器继续找其他重载。

    “约束”就是利用这个机制，让不满足条件的模板自动失效。

    经典写法就是 `std::enable_if`：

    ```cpp
    template<typename T>
    std::enable_if_t<condition, void> foo(T const&);
    ```

    - 条件为 `true`：有这个函数
    - 条件为 `false`：这个函数签名无效，被丢弃

5. **C++** 中 `std::enable_if` 简化版定义：

    ```cpp
    template<bool B, class T = void>
    struct enable_if {};                 // B=false 时，里面没有 type

    template<class T>
    struct enable_if<true, T> {
        using type = T;                  // B=true 时，才有 type
    };
    ```

    **结论**：

    - 条件为 `true`：`enable_if<...>::type` 存在，等于 `T`
    - 条件为 `false`：`enable_if<...>::type` 不存在，模板替换失败，进入 **SFINAE** 丢弃候选

    也可以使用 `std::enable_if_t<cond, T>` 代替 `std::enable_if<cond, T>::type`。

    ```cpp
    {
        std::cout << "Num: " << num << std::endl;
    }
    ```

3. **C++** `static_assert(sizeof(T) == 0, ...)` 详解

    **核心目的**

    这是一种故意触发编译错误的惯用法，用于在模板被实例化时产生友好的错误信息。

    ---

    **为什么 `sizeof(T) == 0` 永远为 `false`？**

    C++ 标准保证任何完整类型的 `sizeof` 至少为 1（即使是空类也是如此）。因此：

    ```cpp
    sizeof(int)      == 4 // ≥ 1
    sizeof(char)     == 1 // ≥ 1
    sizeof(MyStruct) >= 1 // 保证
    ```

    `sizeof(T) == 0` 在任何合法类型上都不可能为真，所以这个 `static_assert` 一旦被编译器实例化，必然触发编译错误。

    ---

    **为什么不直接写 `static_assert(false, ...)`？**

    ```cpp
    // 错误
    template<typename T>
    struct TagTraits {
        static_assert(false, "unsupported type T");
    };
    ```

    许多编译器（尤其是 MSVC 和旧版 GCC）会在模板定义阶段（不等实例化）就对 `static_assert(false)` 报错，导致即使你从未使用该模板也会编译失败。

    ```cpp
    // 正确：依赖模板参数 T，让断言只在实例化时触发
    template<typename T>
    struct TagGetter {
        static_assert(sizeof(T) == 0, "unsupported type T");
    };
    ```

    通过引用 T，断言变为依赖表达式（dependent expression），编译器必须等到模板被实例化时才求值，从而只有当你真正用了不支持的类型时才报错。

1. **C++** 中使用 `size_t` `uint_t` 这类类型时需要加上 `std::` 命名空间：

    在 **C** 语言中，`size_t`、`uint_t` 这些类型定义在：

    ```c
    #include <stdint.h>
    #include <stddef.h>
    ```

    引入后，这些类型直接在全局命名空间可用。

    ---

    在 **C++** 语言中，其提供了两套对应的头文件。对于 C 语言风格的头文件（例如 `stdint.h`）下的类型名称没有命名空间一说，对于 C++ 风格的头文件（例如 `cstdint`）下的类型均处于 `std` 命名空间中。

    并且 **C++** 标准规定：使用 `cstdint` 时，这些类型保证在 `std::` 命名空间中，在全局命名空间是否可用属于 **未定义行为（implementation-defined）**。

    ---

    虽然大多数编译器顺带将这些类型也放进了全局命名空间导致不写 `std::` 也能编译通过，但是这仍然 **不是标准保证的行为**！再加之各个编译器在不断 **收紧对标准的遵守程度**，所以很可能出现“之前能编译通过的代码现在报错”的情况。

    总而言之，在使用诸如 `cstdint` 此类 C++ 风格的头文件时，务必在各类型前面加上 `std::`！

    ---

    *For me（不确定）：已经存在的项目将所有 `cstdint` 此类 C++ 语言风格的头文件全部改写为 `stdint.h` C 语言风格的头文件，以保证在编译器标准程度提高的同时仍然可以使大量存在未使用 `std::` 命名空间的类型或函数的代码编译通过。对于以后的新 C++ 项目则统一使用 C++ 语言风格的头文件，并严格使用 `std::` 命名空间。*

3. **C++** `std::packaged_task` 解析：

    - **引入时间**：C++11
    - **用途**：将一个可调用对象（函数、lambda、函数对象等）封装起来，并把执行结果关联到一个 `std::future` 上。
    - **常见使用场景**：

        - **线程池/任务队列**：把任务封装起来，丢进队列，之后由某个工作线程执行。调用者拿到 `future`，可以异步等待结果。
        - **异步计算**：需要把一个函数延后执行，但又想保留结果获取能力。
        - **将普通函数转换为可调度任务**：方便在不同线程、不同调度器中统一管理。

    - **基本用法**：

        ```cpp
        #include <future>
        #include <iostream>

        int add(int a, int b) {
            return a + b;
        }

        int main() {
            std::packaged_task<int(int, int)> task(add);
            std::future<int> fut = task.get_future();

            task(2, 3);  // 执行任务

            std::cout << fut.get() << std::endl; // 5
        }
        ```

    - **与 `std::async` 区别**：

        - `std::async`：更高层，直接提交异步任务，使用简单。
        - `std::packaged_task`：更底层，用户决定何时、在哪个线程执行，控制更强，适合任务调度系统。

5. 条件变量 `condition_variable` 推荐在锁外发出通知，原因如下：

    在锁内 `notify` 会导致“虚假唤醒再等锁”的情况：被唤醒的线程立即尝试获取互斥锁，但锁仍被通知方持有，导致被唤醒线程再次挂起，产生一次无意义的上下文切换（即 **hurry-up-and-wait** 反模式）。

    ```cpp
    // 不推荐：notify 在锁内
    {
        std::lock_guard<std::mutex> lock(mtx_);
        state_ = true;
        cv_.notify_all(); // 被唤醒的线程立刻因争锁而再次休眠，虽然离开锁的作用域，锁被释放后，其他线程能够正常获取锁，但会浪费性能。
    }

    // 推荐：notify 在锁外
    {
        std::lock_guard<std::mutex> lock(mtx_);
        state_ = true;
    }
    cv_.notify_all();    // 被唤醒时锁已释放，可立即继续执行
    ```

1. **C/C++** 中在头文件中声明并定义的函数推荐使用 `static` 进行修饰。

    如果同一个头文件被多个 `.c`/`.cpp` 文件 `#include`，那么每个编译单元都会生成这些函数的定义，链接时就会报 `multiple definition` 错误。

    **方案对比**：

    | 方式 | 行为 |
    | --- | --- |
    | `static` | 每个编译单元有各自的副本，不共享，二进制稍大 |
    | `inline` | **C99** 语义复杂，需配合 `extern` 定义，不推荐单独用 |
    | `static inline` | 每个单元有副本 + 提示编译器内联，单头文件库的惯用做法 |

    **`inline` VS `static inline`**：

    - `inline`

        在 **C** 语言中，`inline` 的语义与 **C++** 不同：

        **C99** 规定：`inline` 函数必须在某个翻译单元中提供一个 `extern` 的外部定义，否则链接器找不到实际符号会报错。也就是说，`inline void foo() {}` 在 **C** 中只是“建议内联”，本身不提供外部定义。

        **C++** 的 `inline` 具有 **ODR（One Definition Rule（单一定义规则））** 保证，自带多定义保护。

    - `static inline`

        `static` 使函数具有内部链接，每个翻译单元独立拥有一份副本。不需要额外的 `extern` 外部定义，链接器不会产生重复定义或找不到符号的问题。`inline` 使编译器仍然可以选择内联它，也可以生成一个本地的函数实体。

2. **C++** **ODR（One Definition Rule（单一定义规则））**

    - 变量/函数：在整个程序中只能有一个定义（但可以有多个声明）
    - `inline` 函数例外：可以在多个翻译单元中出现相同定义，但所有定义必须完全相同

3. **C/C++** **TU（Translation Unit（翻译单元））**

    在 **C/C++** 中，一个翻译单元就是一个 `.c`/`.cpp` 文件经过预处理后的结果，即编译器每次编译的最小独立单位。

3. **C/C++** 数值类型转换规则

    1. 隐式转换与强制转换（显式转换）对于数值类型，规则相同。强制转换后只是绕过编译器限制，明确表达意图，不会改变运行时行为。（最大的区别在于：对于隐式的窄化转换而言，无论数值是否溢出目标类型，编译器通常都会产生 `narrowing conversion` 警告，使用强转的话则可以消除警告）
    2. 对于窄化转换而言，如果出现了数值溢出，则是未定义行为。所以对于这种情况应该进行 clamp。
    3. 浮点数转换为整数时，如果整数部分溢出目标整数范围、浮点数为 `NAN` 或无穷大则也是未定义行为。

    **规则**：

    1. `double` 转换为 `float` 规则：

        - 如果 float 能够精确表示该值：值保持不变
        - 如果 float 不能精确表示该值：舍入（通常是就近舍入）
        - 如果超出 float 范围：未定义行为（C）；未指定行为（C++）

    2. 整数之间的窄化转换规则：

        - 如果该值超出目标范围，结果由实现定义（通常是截断）（与 UB 一样同样不值得信赖）
        - 无符号与有符号整型之间相互转换时，如果该值超出目标范围，结果由实现定义（通常是位模式保持不变）

    1. 整数提升（§6.3.1.1）：比 `int` 窄的类型（如 `uint8_t`、`int16_t`）先提升为 `int` 或 `unsigned int`。
    2. 精度对齐：两个操作数提升后，若类型不同，则将"秩"较低的那个转换为"秩"较高的类型。有符号/无符号混用时另有规则，但基本原则是精度高的获胜。

    简单来说二元运算的结果类型通常是两个操作数中“更宽”/“精度更高”的那个。

8. **Qt** `Q_DECLARE_METATYPE` 讲解

    `Q_DECLARE_METATYPE` 是一个 Qt 宏，定义于 `qmetatype.h` 头文件中，其本质是向 Qt 的元对象系统声明一个自定义类型，使得 Qt 的各种机制都能识别这个类型。（例如，只有通过此宏注册一个自定义类型后，该类型才可以被 `QVariant` 存取）

    **核心作用**：

    - 让 `QVariant` 支持自定义类型
    - 使直接连接的信号槽支持自定义类型参数传递

    > Qt 元对象系统不知道自定义类型的存在，因此如果要在 `QVariant` 中存储自定义类型，就需要用这个宏注册它。此宏必须在全局作用域中使用，并且使用于类型定义之后。它实际上就是为类型定义一个特殊的模板特化，这样 `QVariant` 才能了解如何使用它。这个模板特化提供了一个静态函数 `qt_metatype_id`，它为该类型分配并返回一个独一无二的 ID。这个 ID 用于 `QVariant` 创建、复制、比较和析构该类型的实例。
    >
    > 在 **Qt6** 与大多数平台上，即使不使用 `Q_DECLARE_METATYPE` 作用于自定义类型，许多功能通常也能正常工作，但这仍然是未定义行为。总之当某个自定义类型需要被 `QVariant` 存取时，都要使用此宏对自定义类型进行注册。

9. **Qt** `qRegisterMetaType` 详解

    将自定义类型注册到 Qt 的元对象系统中，让 Qt 能够识别并在 **运行时** 管理这种类型，定义于 `qmetatype.h` 头文件中。它是让自定义类型能够在以队列连接（通常是跨线程）的信号槽中作为参数传递的关键所在。

    **核心作用**：

    使得自定义类型可用于 `QMetaObject` 中的类型信息，例如 `QObject::property()`，`QObject::setProperty()`，以及 `QMetaProperty::read()` 和 `QMetaProperty::write()` 这些反射相关的函数。

    **注意**：

    - 通常需要在程序启动时（例如 `main()` 函数中）进行使用
    - 自定义类型必须具有公共默认构造函数、公共拷贝函数和公共析构函数
    - 自定义类型必须使用 `Q_DECLARE_METATYPE` 先进行声明

10. **Qt** `Q_DECLARE_METATYPE` 与 `qRegisterMetaType` 简易记忆：

    - 自定义类型需要被 `QVariant` 存取时或是需要通过直接连接（同线程）的信号槽作为参数传递时：使用 `Q_DECLARE_METATYPE`

    - macOS：依赖是 `.dylib` 或 `framework`。应用通常打包为 `.app`，将库放入 `Contents/Frameworks`，并使用 `@rpath` / `@loader_path` 让 Mach-O 加载器找到它们。

3. **CMake** 对于安装/部署阶段的运行时依赖可以通过 `RUNTIME_DEPENDENCY_SET` 进行管理，例如

    ```cmake
    # 收集依赖信息
    install(
        TARGETS TargetName
        RUNTIME_DEPENDENCY_SET TargetNameDeps # 收集 TargetName 的运行时依赖，存入 TargetNameDeps 集合
        RUNTIME DESTINATION bin               # 指定 TargetName 安装到 bin 目录
        BUNDLE DESTINATION .
    )

    # 安装收集到的依赖文件
    install(
        RUNTIME_DEPENDENCY_SET TargetNameDeps
        PRE_EXCLUDE_REGEXES "^api-ms-" "^ext-ms-"    # 排除 Windows 系统核心 DLL
        POST_EXCLUDE_REGEXES ".*system32/.*\.dll"    # 排除系统目录下的 DLL
        DIRECTORIES ${RUNTIME_LIB_DIRS}              # 额外指定查找依赖的目录
        RUNTIME DESTINATION bin
        LIBRARY DESTINATION lib
        FRAMEWORK DESTINATION Frameworks
    )
    ```

    随后执行 `cmake --install build --prefix <发布目录>`：

    - Windows：第三方 DLL 会进入 `bin/`
    - Linux：共享库会进入 `lib/`
    - macOS：`framework` 会进入 `Frameworks/`；`.app` 场景通常还需确保库的 `install name` 使用 `@rpath`。

4. **CMake** 对于 `RUNTIME_DEPENDENCY_SET` 需要进行 **收集依赖信息** 与 **安装依赖文件** 两个步骤，而通过 `RUNTIME_DEPENDENCIES` 可以将这两个独立的步骤合并在一起。

    `RUNTIME_DEPENDENCIES` 的用法与 `RUNTIME_DEPENDENCY_SET` 基本相同，其核心作用是在安装目标文件的同时，自动分析、**收集并安装** 该目标的所有运行时依赖。

## 26-09-17

1. **C++**，`{}`（统一初始化语法 （Uniform Initialization / Brace Initialization））是在 **C++11** 引入的，同时引入的还有 `std::initializer_list`。
2. **C++**，对象构造中，`()` 与 `{}` 的区别：

    1. **缩窄转换（Narrowing Conversion）检查**

        `{}` 会禁止隐式缩窄转换，而 `()` 不会。

        ```cpp
        int x = 3.14; // OK，隐式截断为 3
        int y(3.14);  // OK，同上
        int z{3.14};  // 编译错误：缩窄转换
        ```

    2. **"最令人烦恼的解析"（Most Vexing Parse）**

        `()` 在某些情况下会被解析为函数声明而非对象定义

        ```cpp
        Foo a();      // 声明了一个返回 Foo 的函数！
        Foo b{};      // 明确构造一个 Foo 对象，无歧义
        ```

    3. **与 `std::initializer_list` 的优先级**

        如果类同时有普通构造函数和接受 `std::initializer_list` 的构造函数，`{}` 会优先匹配 `initializer_list` 版本

        ```cpp
        std::vector<int> v1(3, 5);   // [5, 5, 5]  —— 调用 (size_t, T) 构造函数
        std::vector<int> v2{3, 5};   // [3, 5]     —— 调用 initializer_list 构造函数
        ```

    4. **聚合类型（Aggregate）初始化**

        `{}` 可以直接初始化聚合体（无自定义构造函数的结构体/数组），`()` 在 **C++20** 之前不行

        ```cpp
        struct Point { int x, y; };
        Point p{1, 2};    // OK，聚合初始化
        Point q(1, 2);    // C++20 之前错误，C++20 起也支持
        ```

    5. **auto 类型推导的差异**

        ```cpp
        auto a = {1};   // std::initializer_list<int>
        auto b{1};      // C++17起为 int（之前版本行为不一致，曾是 initializer_list）
        auto c(1);      // int
        ```

    在现代 C++ 中，优先使用 `{}` 进行对象构造。

3. **C++**，类的 **Setter** 函数三种写法对比：

    ```cpp
    // 写法 A：const 引用
    void setName(const std::string& v) { name_ = v; }

    // 写法 B：按值 + move
    void setName(std::string v)        { name_ = std::move(v); }

    // 写法 C：重载两个版本
    void setName(const std::string& v) { name_ = v; }
    void setName(std::string&& v)      { name_ = std::move(v); }
    ```

    | 调用方式 | 写法 A（const &） | 写法 B（值+move） | 写法 C（重载） |
    | --- | --- | --- | --- |
    | `setName(lvalue)` | 1 次拷贝 | 1 次拷贝（构造参数）+ 1 次移动（赋给成员） | 1 次拷贝 |
    | `setName(temporary/std::move(x))` | 1 次拷贝（引用绑定到临时对象后仍要拷进成员） | 1 次移动（构造参数）+ 1 次移动（赋给成员） | 1 次移动 |

    故，大多数情况下使用写法 B（值+move）最简单，性能也足够好；对于极端性能敏感的接口才考虑使用写法 C（重载两个版本）；对于写法 A（const 引用）通常只在类型移动代价高/不可移动的情况下使用。当然，对于写法 C，也可以使用模板的万能引用进行实现。

    > 此内容仅适合对对象成员进行赋值的 `Setter` 情景。

## 26-09-21

1. 如果库 A 内嵌了库 B，内嵌的这个行为通常被称为 **vendoring** 而非 **embeding**，对于 **内嵌的** 可以称为 **vendored**。如果在 CMake 中，需要根据条件变量决定库 A 是否使用内嵌的库 B 的话，此条件变量可以被命名为 **A_USE_BUNDLED_B**，对于内嵌后的状态变量则可以被命名为 **A_B_VENDORED**。CMake 示例：

    ```cmake
    set(3RDPARTY “${CMAKE_CURRENT_SOURCE_DIR}/3rdparty”)

    option(A_USE_BUNDLED_B "Use the vendored B instead of requiring an externally installed one" ON)

    if(A_USE_BUNDLED_B)
        set(A_B_VENDORED TRUE)
        if(NOT TARGET B)
            add_subdirectory("${3RDPARTY}/B")
        endif()
        target_link_libraries(${PROJECT_NAME} PUBLIC $<BUILD_INTERFACE:B>)
    else()
        set(A_B_VENDORED FALSE)
        find_package(B REQUIRED)
        target_link_libraries(${PROJECT_NAME} PUBLIC B)
    endif()
    ```

2. **CMake** `$<BUILD_INTERFACE>` 和 `$<INSTALL_INTRFACE>`，对于 `target_link_libraries` 以及其他类似命令而言，如果直接使用目标面的话（例如 `target_link_libraries(${PROJECT_NAME} PUBLIC TARGET_NAME)`），这个目标将会在 **构建树内使用** 和 **导出/安装** 场景下都生效，而在指定了场景后则只会在指定场景中生效。具体而言，对于不同的场景，这两个生成器表达式会被展开为不同的值进以影响构建/安装行为。
