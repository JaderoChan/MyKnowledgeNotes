# 知识总结与错误积累-2026-4

## 26-10-19

1. **Qt** `QPlainTextEdit` 相比 `QTextEdit` 对于纯文本/大文档的性能更好。
2. **Qt** `QLayout::addStretch(0);` 详解：

    `addStretch(int stretch = 0)` 的参数是伸缩因子（stretch factor），表示该伸缩项在分配剩余空间时的权重比例。伸缩因子为 0 时表示该项不参与剩余空间的按比例分配，但它的 `sizeHint` 和 `minimumSize` 仍然会被考虑，但作为“弹簧”的作用几乎消失。

    如果布局中所有项伸缩因子都是 0，那么所有项按各自的 `sizeHint` 分配空间，多余的空白由布局的对齐/边距处理，`addStretch(0)` 不会主动“撑开”。

    总体而言：`addStretch(0)` 本身权重为 0，但作为 `QSpacerItem` 它仍具有扩展倾向，在没有其他竞争者时能吸收多余空间；一旦有 `addStretch(1)` 存在，它就被完全压制。

3. **Qt** `QLineEdit::setText()` 会绕过 `QValidator`，直接设置文本内容。
4. **Qt** `QValidator::validate()` 函数的第二个参数 `int& pos` 代表当前光标在字符串中的位置，其是引用类型，这意味着函数可以更改用户的光标位置以允许验证器在修正输入时同步调整光标位置。
5. **Qt** `QVariant` 的 `isValid()` 函数与 `isNull()` 并不等价

    **核心差异**

    | 函数 | 判断的是什么 | 返回 true 的条件 |
    | --- | --- | --- |
    | `isValid()` | 是否有类型 | 存储的类型不是 `QMetaType::UnknownType` |
    | `isNull()` | 是否没值 | 没有初始化值，或包含空指针 |

6. **Qt** `QFontMetries::horizontalAdvance()` 返回的是从当前文本原点开始，到绘制下一个字符的合适起始位置之间的距离（以像素为单位）。

    `horizontalAdvance()` 返回的是“排版推进距离”，用于排版，当需要把多段文本并排摆放时，可以用这个值来决定下一段文本从哪开始画；`boundingRect().width()` 返回的是“墨迹覆盖范围”，用于获取文本实际渲染出来的像素包围盒。。

    **注意事项**

    对于阿拉伯字符或字符串中间的非间距标记，`horizontalAdvance()` 会给出错误结果，因为它无法处理复杂文本的字形整形（Shaping）。如果需要实现交互式文本控件，官方建议使用 `QTextLayout`。

7. **Qt** `QtTreeView::setIndexWidget()` 设置的 Widget 不会覆盖 Item 的图标部分，它会浮动在单元格内，从图标右侧开始显示。
8. **Qt** 通过 `appendRow()` 将 Item 加入 Model 后，Model 会接管 Item 的所有权，也就是说，如果通过 `removeRow()` 删除了某行 Item，不需要再手动释放其内存。

## 26-10-21

1. **C/C++** C++ 的 `static_cast` 与 C 风格强转区别：

    | 特性 | `static_cast` | C 语言强转 |
    | --- | --- | --- |
    | 编译期检查 | 有，检查类型兼容性 | 几乎无 |
    | 类型安全 | 较高，限制在合理转换内 | 较低，易导致未定义行为 |
    | const 移除 | 不可以 | 可以 |
    | 无关指针转换 | 不可以 | 可以 |
    | 可读性与可搜索性 | 高 | 低 |
    | 本质 | 受限的、语义明确的转换 | 万能的、意图模糊的兜底方案 |

2. **C++** 的结构化绑定总是声明新变量，无法直接使用已有变量，例如：

    ```cpp
    bool ok;
    int  value;
    {
        auto [ok, value] = getResult(); // 此处的 ok、value 并非外层已有变量，而是将外层变量命名遮蔽的新变量。
    }
    ```

    如果需要直接赋值给已有变量可以使用 `std::tie`，例如：

    ```cpp
    #include <tuple> // 必要头文件

    bool ok;
    int  value;
    {
        std::tie(ok, value) = getResult();
    }
    ```

    `std::tie` 会把左值引用打包成 `tuple`，再对 `pair/tuple` 做逐元素赋值。

3. **C++** `std::fstream` 能够使用 `std::filesystem::path` 进行构造。
4. **NFTS**、**exFAT**、**UDFS**、**FAT32** 等现代文件系统使用 Unicode 存储文件名。但是在 Windows API 层面上具有两套版本：

    - 宽字符版（W 版）：如 `CreateFileW`，直接接受 `wchar_t` 字符串。这是 NT 内核下的“原生”形式。
    - ANSI 版（A 版）：如 `CreateFileA`，接受窄字符。系统在内部会将这些窄字符按当前代码页转换成 Unicode，再交给宽字符版处理。

    而由于程序调用的各类标准 API 最终都要回归到系统 API 上去，所以当使用接受窄字符的文件读写 API 时，如果传入的窄字符串无法按照当前代码页转换成 Unicode 时，就会打开失败。所以在标准 C++ 中如果要打开包含非 ASCII 字符文件路径的文件流时，可以先使用宽字符串构造 `std::filesystem::path` 再以此构造 `std::fstream`。

    **macOS** 的上层 API 传入/传出的窄字符串通常使用 UTF-8。**Linux** 内核没有规定编码的使用方式，但是在用户空间同样约定为 UTF-8。所以对于使用 Qt 框架开发的程序，如果需要通过 `QString` 打开一个 C++ 标准文件流可以：

    ```cpp
    #ifdef _WIN32
        std::fstream fs(std::filesystem::path(qpath.toStdWString()));
    #else
        std::fstream fs(std::filesystem::path(qpath.toStdString()));
    #endif
    ```

5. **Qt** `QSignalBlocker` `dimiss()`（Qt6.7+） 和 `unlock()` 区别：

    `unblock()` 是“临时”恢复信号，之后还可以用 `reblock()` 重新阻塞；而 `dismiss()` 是“永久”放弃控制权，调用后该 `QSignalBlocker` 对象就彻底失效了，之后再调用 `unlock()`，`relock()` 将不会产生任何效果，也不会再去碰那个 `QObject`。

6. **Qt** 中虽然能够调用其他类实例的公共信号函数，但是 **非常不推荐**，而且这种做法在 Qt 的不同版本中行为不一致。

    从纯粹的 C++ 语法角度看，信号函数确实是一个成员函数。在 Qt5 及之后的版本中，`signals` 宏被展开为 `public`，这意味着从访问权限上讲，其他类确实可以像调用普通成员函数一样去调用它。但是这违背了 Qt 信号槽的设计初衷，会带来几个实际的问题：

    1. **破坏封装与设计意图**：信号的本意是“通知”，应该由拥有该信号的对象在其状态发生改变时，通过 `emit` 自行发射。从外部强行调用另一个对象的信号，会让代码的因果关系变得混乱。
    2. **版本兼容性风险**：在早期的 Qt4 版本中，信号默认是 `protected` 的，外部类根本无法直接调用。虽然 Qt5 改为了 `public`，但依赖这一实现细节的代码可移植性较差。
    3. **官方文档与社区均不推荐**：Qt 文档虽然承认信号是 `public` 的，但明确建议“只应从定义该信号的类或其子类中发射它”。Qt 社区也普遍认为这不是一种好的做法。

    如果确实需要从外部触发某个对象的信号，更符合 Qt 风格的做法是：

    - **连接信号到信号**：将外部类的一个信号，连接到目标对象的信号上。当外部类发射自己的信号时，目标对象的信号也会被自动触发。
    - **调用公开的成员函数**：在目标类中提供一个公开的方法，由该方法在内部负责 `emit` 信号。外部类调用这个方法即可，这样既实现了功能，又保持了良好的封装。

7. **Qt** `QObject::blockSignals()` 的返回值是调用该函数之前，对象的信号阻塞状态（即 `signalsBlocked()` 的旧值）。

    **典型用途**：

    用于恢复对象之前的阻塞状态。例如，只需要临时阻塞一下信号，之后恢复原样，可以：

    ```cpp
    bool wasBlocked = obj->blockSignals(true);
    // ... 执行一些不触发信号的操作 ...
    obj->blockSignals(wasBlocked); // 恢复到之前的状态
    ```

8. **Qt** 中通过 `QStandardItemModel::setData()` 设置 item 数据通常比直接调用 `QStandardItem::setData()` 性能更好。核心区别在于信号触发的路径与频率。直接操作 `QStandardItem` 的 `setData()`/`setText()` 在特定条件下会触发更耗时的“全量布局刷新”信号，而 `QStandardItemModel::setData()` 走的是更轻量的标准数据变更路径。
9. **Qt** `QStandardItem` 的 `setText()` 只是一个便利函数，其等同于 `setData(QString, Qt::DisplayRole)`；同样，如果需要通过 `QStandardItemModel` 设置指定 item 的文本，可以 ``QStandardItemModel::setData(itemIndex, "Text", Qt::DisplayRole)`。
10. 对于某个循环，如果其性能消耗并非线性增长则需要特别留意循环体中是否包含与回调相关的函数。例如在一个循环体中对 **Qt** 的 `QStandardItem` 修改，则会触发 `dataChanged()` 以及其他与之关联的信号，而这又会调用与之连接的槽函数，容易导致事件累积并卡死 UI，
11. **Qt** `QStandardItem::index()` 函数耗时极短，但本身仍具有轻量运算，其等价于 `QStandardItemModel::indexFromItem(item)`。

## 26-10-23

1. **C++** 函数的默认参数可以是的动态取值的，例如使用其他函数的返回值作为默认参数（调用时取值）。如果希望默认值能够根据同函数之前的参数值动态变化，如 `void foo(int a, int b = 2 * a)` 也是允许的。
2. **Qt** 调色板 `Window` 和 `Base` 区别：

    `QPalette::Window`：代表通用背景色。通常用于非输入类控件的背景，比如普通窗口、标签（`QLabel`）或按钮周围的面板区域。

    `QPalette::Base`：代表文本输入背景色。它主要专门用于需要输入或编辑文本的控件背景，例如 `QLineEdit`、`QTextEdit`，以及 `QComboBox` 的下拉列表等。标准配色下它通常是白色或浅色，以凸显可编辑区域。

3. **Qt** `QColor::lighter()` `QColor::darker()` 函数的作用是返回一个更亮/更暗的颜色。特别注意的是，其参数 `factor` 是倍率因子，这意味着这两个函数是对亮度进行乘法操作而非加法。示例：`color.lighter(150)` 意味着返回的颜色将比原色亮 50%。

    > - 这两个函数的原理是先将 RGB 颜色转换到 HSV 色彩空间，再对 **明度（Value）** 分量乘以倍率，最后再转换回 RGB。
    > - 对 `lighter()`/`darker()` 传入小于 100 的 factor 虽然能够使其产生更暗/更亮（另一方函数产生的效果）的效果，但官方建议始终使用特定的函数。
    > - 如果传入的 factor 为 0 或为负数，返回值是未定义的。

4. **Qt** `QWidget::updateGeometry()` 作用是通知布局系统：该控件的尺寸建议（size hint）或尺寸策略（size policy）已经改变，可能需要重新计算并调整布局。主要用于：自定义控件的内部状态发生变化，导致其推荐尺寸（`sizeHint()`）或最小尺寸（`minimumSizeHint()`）发生改变时，必须手动调用此函数。否则，父级布局管理器不知道需要重新排列控件，可能导致显示不全或布局错乱。
5. **Qt** `QWidget` 被设计为一个轻量级的容器，它的默认 `paintEvent()` 几乎不做任何绘制，只负责最基本的背景擦除，并不会调用样式引擎来绘制背景。因此，如果自定义了一个继承于 `QWidget` 且没有重写 `paintEvent()` 的控件时，对其设置样式表将不起效果，解决办法是在子类中重写 `paintEvent()` 使其显式让样式引擎绘制控件：

    ```cpp
    void MyWidget::paintEvent(QPaintEvent *e) {
        QStyleOption opt;
        opt.initFrom(this);
        QPainter p(this);
        style()->drawPrimitive(QStyle::PE_Widget, &opt, &p, this);
    }
    ```

    此外如果仅仅是想控制自定义控件的背景且不想重写 `paintEvent()` 也可以采用 `setAutoFillBackground(true)` + `QPalette` 的方式。具体来说 `QWidget` 的 `AutoFillBackground` 属性默认是 false，所以 `QWidget` 不会自动使用调色板绘制背景（`AutoFillBackground` 属性的作用就是控制控件在绘制之前是否先填充背景）；而要实现控制自定义控件背景的话，就需要将控件的 `AutoFillBackground` 属性设置为 true，这样自定义控件就会使用其对应的调色板颜色填充背景了。

    > 两种方案通常只能使用其一，同时使用的话可能出现冲突。

6. **Doxygen** 分组指令 `@defgroup`，`@addtogroup` 和 `@name` 除定义组名外还可以附带简略描述和详细描述。
