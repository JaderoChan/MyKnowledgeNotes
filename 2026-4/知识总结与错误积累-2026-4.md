## 26-10-19

1. **Qt** `QPlainTextEdit` 相比 `QTextEdit` 对于纯文本/大文档的性能更好。
2. **Qt** `QLayout::addStretch(0);` 详解：

    `addStretch(int stretch = 0)` 的参数是伸缩因子（stretch factor），表示该伸缩项在分配剩余空间时的权重比例。伸缩因子为 0 时表示该项不参与剩余空间的按比例分配，但它的 `sizeHint` 和 `minimumSize` 仍然会被考虑，但作为“弹簧”的作用几乎消失。

    如果布局中所有项伸缩因子都是 0，那么所有项按各自的 `sizeHint` 分配空间，多余的空白由布局的对齐/边距处理，`addStretch(0)` 不会主动“撑开”。

    总体而言：`addStretch(0)` 本身权重为 0，但作为 `QSpacerItem` 它仍具有扩展倾向，在没有其他竞争者时能吸收多余空间；一旦有 `addStretch(1)` 存在，它就被完全压制。

3. **Qt** `QLineEdit::setText()` 会绕过 `QValidator`，直接设置文本内容。
4. **Qt** `QValidator::validate()` 函数的第二个参数 `int& pos` 代表当前光标在字符串中的位置，其是引用类型，这意味着函数可以更改用户的光标位置以允许验证器在修正输入时同步调整光标位置。
5. **Qt** `QVariant` 的 `isValid()` 函数与 `isNull()` 并不等价

    **核心差异**

    | 函数 | 判断的是什么 | 返回 true 的条件 |
    | --- | --- | --- |
    | `isValid()` | 是否有类型 | 存储的类型不是 `QMetaType::UnknownType` |
    | `isNull()` | 是否没值 | 没有初始化值，或包含空指针 |

6. **Qt** `QFontMetries::horizontalAdvance()` 返回的是从当前文本原点开始，到绘制下一个字符的合适起始位置之间的距离（以像素为单位）。

    `horizontalAdvance()` 返回的是“排版推进距离”，用于排版，当需要把多段文本并排摆放时，可以用这个值来决定下一段文本从哪开始画；`boundingRect().width()` 返回的是“墨迹覆盖范围”，用于获取文本实际渲染出来的像素包围盒。。

    **注意事项**

    对于阿拉伯字符或字符串中间的非间距标记，`horizontalAdvance()` 会给出错误结果，因为它无法处理复杂文本的字形整形（Shaping）。如果需要实现交互式文本控件，官方建议使用 `QTextLayout`。

7. **Qt** `QtTreeView::setIndexWidget()` 设置的 Widget 不会覆盖 Item 的图标部分，它会浮动在单元格内，从图标右侧开始显示。
8. **Qt** 通过 `appendRow()` 将 Item 加入 Model 后，Model 会接管 Item 的所有权，也就是说，如果通过 `removeRow()` 删除了某行 Item，不需要再手动释放其内存。

1. **C/C++** C++ 的 `static_cast` 与 C 风格强转区别：

    | 特性 | `static_cast` | C 语言强转 |
    | --- | --- | --- |
    | 编译期检查 | 有，检查类型兼容性 | 几乎无 |
    | 类型安全 | 较高，限制在合理转换内 | 较低，易导致未定义行为 |
    | const 移除 | 不可以 | 可以 |
    | 无关指针转换 | 不可以 | 可以 |
    | 可读性与可搜索性 | 高 | 低 |
    | 本质 | 受限的、语义明确的转换 | 万能的、意图模糊的兜底方案 |

2. **C++** 的结构化绑定总是声明新变量，无法直接使用已有变量，例如：

    ```cpp
    bool ok;
    int  value;
    {
        auto [ok, value] = getResult(); // 此处的 ok、value 并非外层已有变量，而是将外层变量命名遮蔽的新变量。
    }
    ```

    如果需要直接赋值给已有变量可以使用 `std::tie`，例如：

    ```cpp
    #include <tuple> // 必要头文件

    bool ok;
    int  value;
    {
        std::tie(ok, value) = getResult();
    }
    ```

    `std::tie` 会把左值引用打包成 `tuple`，再对 `pair/tuple` 做逐元素赋值。

3. **C++** `std::fstream` 能够使用 `std::filesystem::path` 进行构造。
4. **NFTS**、**exFAT**、**UDFS**、**FAT32** 等现代文件系统使用 Unicode 存储文件名。但是在 Windows API 层面上具有两套版本：

    - 宽字符版（W 版）：如 `CreateFileW`，直接接受 `wchar_t` 字符串。这是 NT 内核下的“原生”形式。
    - ANSI 版（A 版）：如 `CreateFileA`，接受窄字符。系统在内部会将这些窄字符按当前代码页转换成 Unicode，再交给宽字符版处理。

    而由于程序调用的各类标准 API 最终都要回归到系统 API 上去，所以当使用接受窄字符的文件读写 API 时，如果传入的窄字符串无法按照当前代码页转换成 Unicode 时，就会打开失败。所以在标准 C++ 中如果要打开包含非 ASCII 字符文件路径的文件流时，可以先使用宽字符串构造 `std::filesystem::path` 再以此构造 `std::fstream`。

    **macOS** 的上层 API 传入/传出的窄字符串通常使用 UTF-8。**Linux** 内核没有规定编码的使用方式，但是在用户空间同样约定为 UTF-8。所以对于使用 Qt 框架开发的程序，如果需要通过 `QString` 打开一个 C++ 标准文件流可以：

    ```cpp
    #ifdef _WIN32
        std::fstream fs(std::filesystem::path(qpath.toStdWString()));
    #else
        std::fstream fs(std::filesystem::path(qpath.toStdString()));
    #endif
    ```

5. **Qt** `QSignalBlocker` `dimiss()`（Qt6.7+） 和 `unlock()` 区别：

    `unblock()` 是“临时”恢复信号，之后还可以用 `reblock()` 重新阻塞；而 `dismiss()` 是“永久”放弃控制权，调用后该 `QSignalBlocker` 对象就彻底失效了，之后再调用 `unlock()`，`relock()` 将不会产生任何效果，也不会再去碰那个 `QObject`。

6. **Qt** 中虽然能够调用其他类实例的公共信号函数，但是 **非常不推荐**，而且这种做法在 Qt 的不同版本中行为不一致。

    从纯粹的 C++ 语法角度看，信号函数确实是一个成员函数。在 Qt5 及之后的版本中，`signals` 宏被展开为 `public`，这意味着从访问权限上讲，其他类确实可以像调用普通成员函数一样去调用它。但是这违背了 Qt 信号槽的设计初衷，会带来几个实际的问题：

    1. **破坏封装与设计意图**：信号的本意是“通知”，应该由拥有该信号的对象在其状态发生改变时，通过 `emit` 自行发射。从外部强行调用另一个对象的信号，会让代码的因果关系变得混乱。
    2. **版本兼容性风险**：在早期的 Qt4 版本中，信号默认是 `protected` 的，外部类根本无法直接调用。虽然 Qt5 改为了 `public`，但依赖这一实现细节的代码可移植性较差。
    3. **官方文档与社区均不推荐**：Qt 文档虽然承认信号是 `public` 的，但明确建议“只应从定义该信号的类或其子类中发射它”。Qt 社区也普遍认为这不是一种好的做法。

    如果确实需要从外部触发某个对象的信号，更符合 Qt 风格的做法是：

    - **连接信号到信号**：将外部类的一个信号，连接到目标对象的信号上。当外部类发射自己的信号时，目标对象的信号也会被自动触发。
    - **调用公开的成员函数**：在目标类中提供一个公开的方法，由该方法在内部负责 `emit` 信号。外部类调用这个方法即可，这样既实现了功能，又保持了良好的封装。

7. **Qt** `QObject::blockSignals()` 的返回值是调用该函数之前，对象的信号阻塞状态（即 `signalsBlocked()` 的旧值）。

    **典型用途**：

    用于恢复对象之前的阻塞状态。例如，只需要临时阻塞一下信号，之后恢复原样，可以：

    ```cpp
    bool wasBlocked = obj->blockSignals(true);
    // ... 执行一些不触发信号的操作 ...
    obj->blockSignals(wasBlocked); // 恢复到之前的状态
    ```

8. **Qt** 中通过 `QStandardItemModel::setData()` 设置 item 数据通常比直接调用 `QStandardItem::setData()` 性能更好。核心区别在于信号触发的路径与频率。直接操作 `QStandardItem` 的 `setData()`/`setText()` 在特定条件下会触发更耗时的“全量布局刷新”信号，而 `QStandardItemModel::setData()` 走的是更轻量的标准数据变更路径。
9. **Qt** `QStandardItem` 的 `setText()` 只是一个便利函数，其等同于 `setData(QString, Qt::DisplayRole)`；同样，如果需要通过 `QStandardItemModel` 设置指定 item 的文本，可以 ``QStandardItemModel::setData(itemIndex, "Text", Qt::DisplayRole)`。
10. 对于某个循环，如果其性能消耗并非线性增长则需要特别留意循环体中是否包含与回调相关的函数。例如在一个循环体中对 **Qt** 的 `QStandardItem` 修改，则会触发 `dataChanged()` 以及其他与之关联的信号，而这又会调用与之连接的槽函数，容易导致事件累积并卡死 UI，
11. **Qt** `QStandardItem::index()` 函数耗时极短，但本身仍具有轻量运算，其等价于 `QStandardItemModel::indexFromItem(item)`。

1. **C++** 函数的默认参数可以是的动态取值的，例如使用其他函数的返回值作为默认参数（调用时取值）。如果希望默认值能够根据同函数之前的参数值动态变化，如 `void foo(int a, int b = 2 * a)` 也是允许的。
2. **Qt** 调色板 `Window` 和 `Base` 区别：

    `QPalette::Window`：代表通用背景色。通常用于非输入类控件的背景，比如普通窗口、标签（`QLabel`）或按钮周围的面板区域。

    `QPalette::Base`：代表文本输入背景色。它主要专门用于需要输入或编辑文本的控件背景，例如 `QLineEdit`、`QTextEdit`，以及 `QComboBox` 的下拉列表等。标准配色下它通常是白色或浅色，以凸显可编辑区域。

3. **Qt** `QColor::lighter()` `QColor::darker()` 函数的作用是返回一个更亮/更暗的颜色。特别注意的是，其参数 `factor` 是倍率因子，这意味着这两个函数是对亮度进行乘法操作而非加法。示例：`color.lighter(150)` 意味着返回的颜色将比原色亮 50%。

    > - 这两个函数的原理是先将 RGB 颜色转换到 HSV 色彩空间，再对 **明度（Value）** 分量乘以倍率，最后再转换回 RGB。
    > - 对 `lighter()`/`darker()` 传入小于 100 的 factor 虽然能够使其产生更暗/更亮（另一方函数产生的效果）的效果，但官方建议始终使用特定的函数。
    > - 如果传入的 factor 为 0 或为负数，返回值是未定义的。

4. **Qt** `QWidget::updateGeometry()` 作用是通知布局系统：该控件的尺寸建议（size hint）或尺寸策略（size policy）已经改变，可能需要重新计算并调整布局。主要用于：自定义控件的内部状态发生变化，导致其推荐尺寸（`sizeHint()`）或最小尺寸（`minimumSizeHint()`）发生改变时，必须手动调用此函数。否则，父级布局管理器不知道需要重新排列控件，可能导致显示不全或布局错乱。
5. **Qt** `QWidget` 被设计为一个轻量级的容器，它的默认 `paintEvent()` 几乎不做任何绘制，只负责最基本的背景擦除，并不会调用样式引擎来绘制背景。因此，如果自定义了一个继承于 `QWidget` 且没有重写 `paintEvent()` 的控件时，对其设置样式表将不起效果，解决办法是在子类中重写 `paintEvent()` 使其显式让样式引擎绘制控件：

    ```cpp
    void MyWidget::paintEvent(QPaintEvent *e) {
        QStyleOption opt;
        opt.initFrom(this);
        QPainter p(this);
        style()->drawPrimitive(QStyle::PE_Widget, &opt, &p, this);
    }
    ```

    此外如果仅仅是想控制自定义控件的背景且不想重写 `paintEvent()` 也可以采用 `setAutoFillBackground(true)` + `QPalette` 的方式。具体来说 `QWidget` 的 `AutoFillBackground` 属性默认是 false，所以 `QWidget` 不会自动使用调色板绘制背景（`AutoFillBackground` 属性的作用就是控制控件在绘制之前是否先填充背景）；而要实现控制自定义控件背景的话，就需要将控件的 `AutoFillBackground` 属性设置为 true，这样自定义控件就会使用其对应的调色板颜色填充背景了。

    > 两种方案通常只能使用其一，同时使用的话可能出现冲突。

6. **Doxygen** 分组指令 `@defgroup`，`@addtogroup` 和 `@name` 除定义组名外还可以附带简略描述和详细描述。

1. **C++17** 及以上对于路径的存储/处理应该使用 `std::filesystem::path` 而不是字符串。
2. Windows 下对于只接受窄字符的 File IO API（例如 OpenCV 中的 VideoCapture）。如果需要其能够处理包含非 ASCII 字符路径的文件，可以先构建一个位于磁盘根目录下仅包含 ASCII 字符的符号链接/硬链接，然后将符号链接的文件路径传入窄字符文件路径 API。
3. **OpenCV** 空图像（`cv::Mat::empty() == true`）的 `type()` 是 `CV_8UC1`，所以在处理图像色彩转换时，不能仅通过其 type 值做后续处理，必须先判断图像是否为空，否则将会引发断言失败。
4. **C++** `std::filesystem::path` 成员函数介绍：

    - `extension()`：返回路径中 **文件名部分** 的扩展名，返回值是一个 `std::filesystem::path` 对象，且 **包含前导的点号**。

        **返回值规则**：

        - **常规情况**：返回从最右侧的点号（包含该点号）开始到文件名末尾的子串。例如 `/foo/bar.txt` 返回 `.txt`。
        - **以点号开头的文件**：如果文件名第一个字符是点号（如 `.profile`），该点号不被视为扩展名的开始，函数返回空路径 `""`。
        - **无扩展名或特殊路径**：如果文件名中不含点号，或者路径是 `.`/`..`，返回空路径 `""`。
        - **以点号结尾**：如果文件名以点号结尾（如 `file.`），函数返回 `"."`，以此区分“无扩展名”（返回 `""`）的情况。

    - `filename()`：返回路径中 **最右侧的文件名或目录名组件**。

        **返回值规则**：

        - **常规情况**：返回最后一个路径分隔符之后的部分。例如 `/foo/bar.txt` 返回 `bar.txt`。
        - **以点号开头的文件**：例如 `/foo/.bar` 返回 `.bar`。
        - **特殊路径**：如果路径以 `.`/`..` 结尾，则分别返回 `.` 或 `..`。
        - **以分隔符结尾**：如果路径以目录分隔符结尾（如 `/foo/bar/`），根据标准等价规则，它通常返回空路径。但在某些实现（如 Microsoft 文档中提到的旧版行为）中可能会返回 `.`，这属于实现细节差异。
        - **空路径**：返回空路径。

    - `rootname()`：返回路径的根名称，用于标识多根文件系统中的根（例如 Windows 的盘符 `"C:"` 或网络路径 `"//myserver"`）。

        如果路径不包含根名称（例如 POSIX 风格路径 `/foo/bar`），则返回空路径 `path()`。

        **示例**：对于 `"C:\\Users\\test.txt"`，返回 `"C:"`；对于 `"/home/user"`，返回空路径。

    - `stem()`：返回 `filename()` 中去掉最后一段扩展名后的部分。

        - **核心规则**：取文件名从开头到最后一个点号（`.`）之前的子串（不包括该点号）。
        - **特殊例外**：

            - 若文件名以点号开头（如 `.profile`），该点号不被视为扩展名分隔符，返回整个 `.profile`。
            - 若文件名是 `.` 或 `..`，或完全不包含点号，则返回整个 `filename()`。

        - **示例**：`"foo.bar.baz.tar"` 的 `stem()` 返回 `"foo.bar.baz"`；`"/foo/bar.txt"` 返回 `"bar"`。

## 26-10-30

1. **Qt** `QWidget` 只能设置一个顶层 Layout，如果对同一 Widget 调用多次 `setLayout()`，后设置的布局并不会覆盖先前的布局，通常会输出警告。如果需要调整界面布局，可以先删除旧布局在设置新布局，例如：

    ```cpp
    if (QLayout *oldLayout = widget->layout())
        delete oldLayout;

    auto *newLayout = new QVBoxLayout;
    widget->setLayout(newLayout);
    ```

    > 注意，旧布局管理的控件对象并不会被删除。

2. **Qt** 直接对 Widget 设置 Layout 和创建 Layout 时指定 Widget 父对象，这两种写法效果基本相同，区别只有布局的安装时机不同（前者在安装前可以先对 Layout 进行配置，后者是构造时直接安装）；对于后者，其同样受上一条日记所描述的约束。
3. **Qt** `delete` 和 `deleteLater()` 区别：

    - `delete` 会立即销毁对象。
    - `deleteLater()` 只是安排对象在合适的事件循环时机销毁，调用后对象并没有立刻消失。

    调用 `deleteLater()` 后可以将指针置为 `nullptr`，这样这个指针变量就不会被误用，但不会让对象提前销毁，也不会自动清空其他指向它的裸指针。如果需要跟踪对象是否仍存在，可以用 `QPointer<T>`；对象销毁后它会自动变成 `nullptr`。

    在信号槽或事件处理过程中，直接 `delete` 可能让正在执行的代码继续访问已销毁对象；这种场景通常用 `deleteLater()` 更稳妥。它依赖事件循环处理延迟删除事件。

4. **Qt** `QStackedWidget::addWidget()` 如果当前 `QStackedWidget` 为空（`currentIndex` 为 -1 时），会同时改变 `currentIndex` 将新添加的部件设为当前部件；如果当前栈中非空则只是将新部件追加至内部列表末尾，不会自动切换当前显示的部件，`currentIndex` 保持原值不变。`QStackedWidget::insertWidget()` 同样如此。
5. **Qt** 给 `QStackedWidget` 的 `currentIndex` 设置为 -1 时会隐藏所有已添加的页面。
6. **Qt** `QImage` 和 `QPixmap` 区别：`QImage` 是面向 I/O、像素操作且与硬件无关的图像容器，适合在后台线程处理；`QPixmap` 是专为屏幕显示优化、依赖底层窗口系统的图像表示，适合在 GUI 线程快速绘图。
7. **Qt** [`Q_OBJECT` 宏作用](./[Qt]%20Q_OBJECT%20宏作用.md)

## 26-10-31

1. **C/C++** 无符号整数溢出是定义良好的行为（回绕）；有符号整数溢出是未定义行为，这意味着编译器可以假定这种情况永远不会发生，并可能基于此进行激进的优化。例如，对于 `int x`，表达式 `x + 1 > x` 在编译器看来恒为真，因为如果 `x` 是 `INT_MAX`，`x + 1` 就会触发 UB，而 UB 的程序本身没有语义约束。
2. **Qt** `QToolButton::setAutoRaise()` 作用是控制工具按钮的视觉边框显示逻辑，当设置为 `true` 时，按钮平时不显示边框（看起来就像是融入了背景），只有当鼠标指针悬停在上方时才会绘制三维的凸起边框（即“自动浮起”）。该功能默认是关闭的（`false`），不过当按钮被放进 `QToolBar` 里，这个功能会自动启用。
3. **Qt** `QStackedWidget` 调用 `setCurrentWidget()` 后，如果传入的部件没有被添加进来则会调用失败，不会切换页面（特殊情况：如果当前 `QStackedWidget` 中一个页面都没有则会将传入的 `widget` 作为当前部件）；如果传入的部件是已被添加的，则能够成功切换页面，并同步更改 `currentIndex`。

3. **Qt** `QTimer::singleShot()` 是一个静态便利函数，用于在指定延迟后执行一次性的任务，而不必创建、启动并手动管理一个 `QTimer` 对象实例。

    **常见重载形式**：

    ```cpp
    QTimer::singleShot(int msec, const QObject *receiver, PointerToMemberFunction method);
    QTimer::singleShot(int msec, Functor functor);
    QTimer::singleShot(int msec, Qt::TimerType timerType, Functor functor);
    ```

    **用途与特点**：

    - **一次性延迟任务**：常用于延迟执行某个槽函数或 lambda，例如延迟隐藏提示框、延迟发起一次请求、在事件循环启动后执行初始化逻辑（`singleShot(0, ...)`）等。
    - **自动销毁、无需手动管理**：内部由 Qt 创建一个一次性触发的定时器对象，触发后自动停止并释放，调用方无需持有 `QTimer` 实例，也不用担心忘记 `stop()`。
    - **接收者感知生命周期**：如果传入了 `receiver`（`QObject*`），当定时器触发前 `receiver` 被销毁，则该次调用会被自动取消，不会出现回调访问已销毁对象的问题；而纯 `Functor` 版本（不带 `receiver`）不具备这种保护，需要调用方自行保证闭包捕获的对象在触发时仍然有效。
    - **`msec` 为 0**：表示在当前事件循环处理完所有待处理事件后尽快触发一次，常用于把某些逻辑推迟到“下一轮事件循环”执行，避免在当前调用栈中进行耗时或可能引发重入的操作。

## 26-11-05

1. **Qt** 如果尝试从容器组件中（`QLayout`、`QStackedWidget` 等） `removeWidget()` 一个容器中不存在的控件将不会有任何效果，也不会报错。
2. **Qt** `QLayout::addWidget()` 底层过程：将控件从原有布局删除 -> 添加控件至新布局。如果对同一个布局重复添加同一个控件，结果就是“移动控件至布局末端位置”。
3. **Qt** `QFileDialog::getOpen/SaveFileName()` 第三个参数 `dir` 传入文件路径而非目录路径的效果：

    Qt 会将该路径拆解：将文件所在目录设为对话框的当前工作目录，并将该文件名自动填入“保存”对话框的文件名输入框并选中。

4. **OpenCV** `imread()` `imwrite()` 失败处理：

    这两个函数通常不会抛出异常，而是通过无效的返回值（例如 `imread()` 遇到文件不存在、权限不足、格式不支持或文件已损坏时返回空矩阵；`imwrite()` 遇到目录不存在、权限不足、路径无效时返回 `false`）指示错误；但是在极特殊的情况下仍有可能抛出 `cv::Exception`，所以对于某些场景，这两个函数也要加上 `try-catch` 保护。

    抛出异常的可能场景：传入的文件路径的文件扩展名使 OpenCV 无法找到对应的编码器。

5. **C++** **C++11** 引入了 **引用限定符（ref-qualifier）**，他们的表现形式是在成员函数的参数列表之后加上 `&`/`&&`，作用是限制该成员函数只能被左值对象或右值对象调用，并参与重载决议。

    **核心作用/区别**：

    ---

    - **`&`（左值引用限定）**：该函数只能被左值对象调用。如果对一个右值临时对象调用此函数，编译会失败（除非有对应的 `&&` 重载）。
    - **`&&`（右值引用限定）**：该函数只能被右值对象调用（例如临时对象或 `std::move` 后的对象）。
    - 不带限定符：普通的成员函数，左值和右值对象都可以调用它。

    **使用场景**：

    ---

    根据对象的值类别（左值/右值）来优化资源获取或移动语义。

    最经典的例子是实现类似 `std::optional` 的 `get()` 函数：当对象是左值时，返回内部数据的引用（拷贝）；当对象是右值时，返回内部数据的右值引用（允许移动），从而避免不必要的深拷贝。

    ```cpp
    class MyOptional
    {
        T value_;

    public:
        // 左值对象调用：返回左值引用，允许修改或拷贝
        T& get() & { return value_; }

        // 右值对象调用：返回右值引用，允许将内部资源“移动”出去
        T&& get() && { return std::move(value_); }
    };

    MyOptional opt;
    auto& a = opt.get();             // 调用 & 版本，a 绑定到内部成员
    auto  b = std::move(opt).get();  // 调用 && 版本，b 移动构造自内部成员
    ```

    > 引用限定符常与 const 配合使用。例如 const & 限定的函数可被左值和右值调用（因为右值可绑定到 const 左值引用），但函数内不能修改对象；const && 则限定了只能被 const 右值调用。

6. **Qt** `QScrollArea` 通常需要设置 `setWidgetResizable()` 为 `true`，因为 `QScrollArea` 不会自动管理内容控件的尺寸（内容控件将保持它自己内部布局计算出来的固定尺寸），如果这个内容控件的尺寸大小比视口的尺寸小，其显示出来就会“紧贴在视口的左上角”，右边和底边就会空白一片；通过设置 `setWidgetResizable()` 为 `true` 后，如果内容控件的尺寸小于视口尺寸，其会自动将内容控件拉伸到视口大小，如果内容控件尺寸大于视口尺寸，则会出现滚动条。

## 26-11-10

1. **Qt** 中如果需要持久化保存窗口的几何信息以及状态应该使用 `QWidget::saveGeometry()`（通常在使用在 `closeEvent` 中），恢复窗口时使用 `QWidget::restoreGemetry()`。相比于使用 `normalGeometry()` 等方法，`save/restoreGeometry()` 方法是官方推荐的做法，其能自动处理窗口最大化状态与普通 Geometry，并在恢复时检查屏幕边界等。
2. UTF-8 是 ASCII 安全的，这意味着所有多字节字符的每个字节都 **>= 0x80**；所以仅针对 ASCII 字符串的处理函数通常也能在 UTF-8 字符串中正常工作（例如对文本中的特殊 ASCII 字符进行转义）。
3. **Qt** QString 内部使用 UTF-16 编码，`QString::fromStdString()` 返回 UTF-8 字符串，`QString::toStdString()` 则假定传入字符串为 UTF-8 编码。
4. **C++** `std::filesystem::path` 以 `std::string` 构造时假定字符串为本地窄字符编码，`string()` 成员函数的返回值也是本地窄字符编码字符串，窄字符编码在 Windows 上为 ANSI 编码，而在 macOS 和 Linux 等 POSIX 系统上通常就是 UTF-8 编码。
5. **C++** `wchar_t` 在 Windows 上为 2 字节，因此 `std::wstring` 通常用于存储 UTF-16 编码的字符串；在 POSIX 系统上，`wchar_t` 通常为 4 字节，因此 `std::wstring` 用于存储 UTF-32 编码的字符串。C++ 标准并未规定 `wchar_t` 的具体大小，它只是“能够表示受支持区域设置中最大扩展字符集”的整数类型。因此，依赖 `std::wstring` 进行跨平台数据交换是不安全的，因为同一个字符串在不同平台上底层的内存表示（编码）可能完全不同。

    如果需要进行明确的 Unicode 处理或跨平台交换，优先使用 `std::string`（配合 UTF-8）或 C++11 引入的 `std::u16string`/`std::u32string`。

1. macOS App Bundle（.app）是只读结构，不能在程序运行时更改其内容。
2. **Qt** 获取用户偏好设置文件夹位置：`QStandardPaths::writableLocation(QStandardPaths::AppConfigLocation)`。在 macOS 上其对应的路径格式为 `~/Library/Preferences/<APPNAME>`；在 Windows 上其对应的路径格式为 `C:/Users/<USER>/AppData/Local/<APPNAME>`；在 Linux 上其对应的路径格式为 `~/.config/<APPNAME>`；在 Android 上其对应的路径格式为 `<APPROOT>/files/settings`；在 IOS 上其对应的路径格式为 `<APPROOT>/Library/Preferences/<APPNAME>`。其中，`<APPNAME>` 通常由组织名和应用名决定，也可能是二者的组合；`<APPROOT>` 指应用程序的安装位置，在移动平台上通常处于沙盒环境内；`<USER>` 代表当前系统用户名。
